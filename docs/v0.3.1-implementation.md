### 工作项 #1 — P1-2:review 门禁 fail-closed

#### 问题诊断(5Why 归因)

```
现象: GateRunner 缺失时 review 门禁返回 ok=True → 门禁 fail-open
Why1: 为什么 ok=True?   → _gate_review 第 757-758 行硬编码跳过
Why2: 为什么要跳过?    → MVP 阶段 GateRunner 不一定注入
Why3: 为什么不阻断?    → 设计意图是 ci_green 走 advisory
Why4: 为什么不显式标记? → 没有 fail_closed 配置项
Why5: 根因            → 缺少"门禁缺失时如何降级"的统一策略

归因:ROOT 维度 — 缺乏降级矩阵的统一定义
手册对应:模块 4(方案选型)= 损益 + 概率 + 灰度
```

#### 修复方案

**当前代码**(`state_machine.py:756-759`):

```python

    if self.gate_runner is None:
        return {"ok": True, "message": "GateRunner 未注入，跳过 ci_green"}
    return self.gate_runner.run_ci_green()
```

**修复后**:

```python
def _gate_review(self) -> dict:
    """P1-2 修复:GateRunner 缺失时显式 fail-closed

    策略:门禁是 MVP 信任根,缺失即阻断,由用户在 sop.yaml 中显式 disabled.
    不再 fail-open.降级路径由 sop.yaml 的 gates.ci_green.enabled 控制.
    """
    if self.gate_runner is None:
        # 改为阻断,要求显式声明降级
        return {
            "ok": False,
            "message": (
                "review_gate 门禁 fail-closed(P1-2):"
                "GateRunner 未注入.如需降级,请在 sop.yaml 中设置"
                "gates.ci_green.enabled: false 并明确承担风险"
            ),
            "blocking": True,
            "degradation_path": "sop.yaml: gates.ci_green.enabled = false",
        }
    return self.gate_runner.run_ci_green()
```

- ✅ **CLI 行为不变**:正常场景(GateRunner 已注入)继续跑
- ⚠️ **新增 fail-closed**:若用户曾依赖"GateRunner 缺失自动通过",会失败
- 🔧 **迁移建议**:在 `devflow init` 输出中提示降级路径

### 工作项 #2 — P1-5:5 条红线显式 mvp_skip 标记

#### 问题诊断(归因 + 系统)

```
现象: 5 条红线(_check_skip_phase / doc_drift / silent_legacy / no_contract / human_step_auto)返回 []
Why1: 为什么返回空?   → 没法自动检测,直接 pass
Why2: 为什么不标记?   → 早期设计假设"由状态机/门禁间接保障"
Why3: 为什么给假象?  → audit 输出空 list 用户误以为"已检查全通过"
Why4: 为什么不告知?  → 缺少 violation 状态的标准化
Why5: 根因          → 缺少「检测能力分级」语义

归因:OWNER 不清 + 状态语义模糊
手册对应:模块 5 优化 = 二八(影响最大的是对外可见性)+ 系统思维(全链路透明)
```

#### 修复方案

**当前代码**(`redline_auditor.py:164-177`):

```python
def _check_skip_phase(self) -> list[RedLineViolation]:
    return []  # 由状态机的不可跳步机制保障

def _check_doc_drift(self) -> list[RedLineViolation]:

# ... 5 条同模式
```

**修复后**(改造 `audit()` 方法,统一定义检测能力):

```python
def audit(self) -> list[RedLineViolation]:
    """执行全量红线扫描

    P1-5 修复:对未实现的红线显式返回 mvp_skip 状态的 violation,
    让用户清楚知道哪些红线**没检查**,而不是被"空 list"误导.
    """
    violations: list[RedLineViolation] = []
    for red_line in self.config.red_lines:
        # mvp_skip 配置优先(已有 circular_dep 走这条)
        if red_line.mvp_skip:
            violations.append(RedLineViolation(
                red_line.name,
                f"红线 '{red_line.name}' 在 MVP 中跳过检测 (mvp_skip: true)",
                skip=True,
            ))
            continue

        # P1-5:对配置启用但未实现自动检测的红线,显式标记 not_implemented
        checker = getattr(self, f"_check_{red_line.name}", None)
        if checker is None:
            violations.append(RedLineViolation(
                red_line.name,
                f"红线 '{red_line.name}' 缺少自动检测实现 (not_implemented)",
                skip=True,
                status="not_implemented",  # 新字段
            ))
            continue

        # 检查函数存在但实现为空(返回 [])→ 标记 stub
        result = checker()
        if not result:
            violations.append(RedLineViolation(
                red_line.name,
                f"红线 '{red_line.name}' 检测实现为 stub (需人工/状态机保障)",
                skip=True,
                status="stub",
            ))
            continue

        violations.extend(result)
    return violations
```

**新增字段**:`RedLineViolation.status` 字段(可选值:`"active" | "mvp_skip" | "not_implemented" | "stub"`)

#### 兼容性影响

- ✅ **CLI 行为**:违规数从 0 变为 5(stub)+ 1(mvp_skip),需在 README 中说明
- ⚠️ **统计变化**:现有 `total_violations` 包含 stub,需新增 `real_violations` 字段
- 🔧 **输出增强**:`devflow audit` 输出加"检测覆盖度"摘要

### 工作项 #3 — P1-9:ci_green 接真实 pytest --cov

#### 问题诊断(系统思维)

```
现象: ci_green 门禁命令为 "echo ci-check-placeholder && exit 0"
Why1: 为什么不接真 CI? → MVP 阶段无 CI 配置
Why2: 为什么放占位?   → 避免阻塞,advisory 模式
Why3: 为什么不接 pytest? → 已存在 tests_pass 门禁,看似重复
Why4: 为什么需要再测? → tests_pass 是 verify 阶段,ci_green 是 review 阶段
Why5: 根因          → 两者边界模糊 + 都用 pytest → 应该差异化

归因:门禁职责重叠 → tests_pass(快测)vs ci_green(覆盖度)
手册对应:模块 5 + DO 假设思维(覆盖度作为合理信号)+ 反馈(覆盖率达阈值给 PASS)
```

#### 修复方案


**修复后**:

```yaml
  blocking: false  # 保留 advisory,但命令真实化
  enabled: true
  bind_to_stage: 6
  note: "P1-9 修复:接真实 pytest --cov,覆盖率阈值 70%,advisory 模式不阻断"
  coverage_threshold: 70
```

**`gate_runner.py` 微调**(适配 coverage 输出):

```python
def run_ci_green(self) -> dict:
    """执行 ci_green 门禁(advisory)

    P1-9 修复:接真实 pytest --cov,捕获覆盖率
    失败时记录覆盖率数值,advisory 模式不阻断但提供反馈信号
    """
    gate = self.config.get_gate("ci_green")
    if gate is None or not gate.enabled:
        return {"ok": True, "message": "ci_green 门禁未启用，跳过"}
    if gate.command is None:
        return {"ok": True, "message": "ci_green 门禁无命令，跳过"}
    result = self._execute_command(gate.command)

    # 提取覆盖率数值
    coverage = self._extract_coverage(result["stdout"])

    # advisory 模式:执行完成即可,不阻断
    return {
        "ok": True,
        "message": (
            f"ci_green 已执行 (exit code {result['returncode']}, "
            f"覆盖率 {coverage}%)，advisory 不阻断"
        ),
        "coverage": coverage,
        "exit_code": result["returncode"],
    }

def _extract_coverage(self, stdout: str) -> Optional[int]:
    """从 pytest --cov 输出提取 TOTAL 覆盖率百分比"""
    import re
    match = re.search(r"TOTAL\s+\d+\s+\d+\s+(\d+)%", stdout)
    if match:
        return int(match.group(1))
    return None
```

#### 兼容性影响

- ✅ **行为不变**:advisory 模式不阻断
- ✅ **新信号**:`devflow status` 显示当前覆盖率
- ⚠️ **依赖扩展**:需在 `pyproject.toml` 加 `pytest-cov` 依赖

### 工作项 #4 — P1-13:review ↔ ledger 双向引用

#### 问题诊断(边界 + 闭环)

```
现象: LedgerEntry 没有 review_id 字段,ReviewReport 也没有 ledger_ref
Why1: 为什么没关联? → 早期设计假设各自完整,无需交叉
Why2: 为什么需要关联? → 审计场景需要"这个违规是哪轮评审发现的"
Why3: 为什么需要双向? → 既要 review → ledger,也要 ledger → review
Why4: 为什么不加字段? → 担心破坏哈希链兼容性
Why5: 根因          → 缺少审计维度的设计

归因:SAY 维度 — 沟通协作断层(评审与账本互不知)
手册对应:模块 6(跨模块)= 边界(账本 schema 不变)+ 闭环(双向引用)+ 博弈(谁依赖谁)
```

#### 修复方案

**扩展 LedgerEntry**(`model/ledger.py`,新增 2 个字段):

```python
class LedgerEntry(BaseModel):
    """账本条目

    P1-13 修复:增加 review_id 字段引用 ReviewReport.id
    哈希链仍然只哈希核心字段(phase/action/timestamp/details),
    新字段为可选不参与哈希.
    """
    phase: int = Field(..., description="阶段号 0-7")
    task_id: Optional[str] = Field(default=None, description="关联的 Task ID")
    action: LedgerAction = Field(..., description="动作类型")
    commit: Optional[str] = Field(default=None, description="git SHA")
    acceptance: Optional[str] = Field(default=None, description="验收结论")
    reason: Optional[str] = Field(default=None, description="skip/ruling 时的原因")
    timestamp: datetime = Field(default_factory=datetime.now)
    details: Optional[str] = Field(default=None, description="附加信息")

    # P1-13 新增字段(可选,不参与哈希链)
    review_id: Optional[str] = Field(
        default=None,
        description="P1-13:关联的 ReviewReport.id"
    )
    actor: Optional[str] = Field(
        default=None,
        description="P1-13 兼 P1-10 预留:操作者标识"
    )
```

**关键设计决策**:

1. **新字段不破坏哈希链**:`_hash/_prev_hash` 只覆盖核心字段(`phase/action/timestamp/details`),向后兼容旧账本
2. **可选字段**:`review_id/actor` 默认 None,旧账本可正常 verify
3. **写入时机**:`review_engine.py` 写账本时填入 `review_id`

**修改 review_engine.py**(4 处调用点统一加 review_id):
