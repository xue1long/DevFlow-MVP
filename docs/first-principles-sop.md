# DevFlow 第一性原理 SOP（v0.1）

> **目的**：把"第一性原理"贯穿"方案 → 评审 → 整改 → 复核"4 个阶段，避免 AI 在错的问题上做对的事。
>
> **与 [`audit-prompt-template-v0.1.md`](./audit-prompt-template-v0.1.md) 的关系**：后者是"挑 bug"的模板，本文档是"质疑方案 + 拒绝无效修复"的元方法。

## 1. 为什么需要第一性原理？

### 1.1 AI 现状的根问题

```
【方案阶段】AI 给方案：    "这是个好方案"  ← 没有验证根假设
【评审阶段】4 角色找问题： "这里有个 bug" ← 评审的是实现，不质疑方案
【整改阶段】改代码：        "按评审改"    ← 可能修了表象，留下根问题
【复核阶段】验证清单：      "都改完了"    ← 没验证根问题是否消除
```

**根问题**：4 个阶段都缺乏"从根上推演"能力。AI 容易陷入"机械执行评审反馈"的循环。

### 1.2 第一性原理的核心思想

> **不预设"必须这样做"，从最基本的约束/事实出发，重新推演最优解。**

应用到 DevFlow：

- **方案阶段**：不要直接给方案，先拆"用户真正在解决什么"
- **评审阶段**：除了挑 bug，要质疑"为什么这是必须做的"
- **整改阶段**：每改一处，问"根问题消除了吗"
- **复核阶段**：核对清单之外，验证"根假设还站得住吗"

### 1.3 第一性 vs. 表面优化的本质区别

| 维度 | 表面优化 | 第一性原理 |
|------|----------|------------|
| **起点** | "现有方案基础上改进" | "回到根本问题重新推演" |
| **问题定义** | 接受用户表述 | 拆解真正诉求 |
| **解决方案** | 在约束内选最优 | 必要时打破约束 |
| **评审关注** | 实现细节 | 根假设是否成立 |
| **验证标准** | "清单全过" | "根问题已消除" |

## 2. 第一性原理 SOP：4 阶段框架

### 阶段 A：方案生成 — 拆表象

**目标**：不直接给方案，先回答 5 个根问题。

#### 5 步拆解 SOP

**步骤 1 — 表象**：用户表面在说什么？

> 例："我想要文件按阶段分类到子目录里"

**步骤 2 — 真问题**：剥掉表象后，用户真正想解决什么？

> 例："我想让已完成的项目有归宿、不污染工作目录、能批量处理"

**步骤 3 — 根假设**：我的初步方案基于哪些假设？哪些可能错？

> 例：
> - 假设 A：用户一定需要"按 Spec 分目录"
> - 假设 B：物理移动文件是必须的
> - 假设 C：账本路径引用不会破坏

**步骤 4 — 替代方案**：不考虑"必须这样做"，还有什么方案？

> 例：
> - 替代 1：不移动文件，只在账本标记（软归档）
> - 替代 2：完全不动结构，加 INDEX 元数据
> - 替代 3：用数据库替代文件

**步骤 5 — 对齐约束**：在真实约束下，哪个方案最合适？

> 例：账本哈希链不可破坏 + 迁移成本高 → 选替代 2

#### 输出格式（方案文档开头）

```markdown
## 第一性分析（必填）

### 1. 表象
[用户表面在说什么]

### 2. 真问题
[剥掉表象后的核心诉求]

### 3. 根假设
- [假设 1]
- [假设 2]

### 4. 替代方案
- [替代 1]
- [替代 2]

### 5. 最终方案 + 对齐依据
[为什么选这个方案]

### 6. 根风险
[选这个方案可能失败的根因]
```

### 阶段 B：评审 — 质疑根假设

**目标**：除了挑 bug，要质疑"这个方案本身是否该做"。

#### 4 角色 + 1 第一性质疑者

**角色 1-4（沿用现有）**：
- 落地执行者、风险管控者、逆向挑战者、最终验收人

**角色 5（新增）：第一性质疑者**

```text
## 角色：第一性质疑者

你的任务是**质疑方案的根假设**，不评审实现细节。

视角：
1. 这个方案在解决"真问题"还是"伪问题"？
2. 方案的根假设是什么？这些假设是否被验证？
3. 如果删掉某些功能/约束，方案能否更简单？
4. 历史类似问题怎么解决的？被复用了吗？
5. 第一性分析（方案文档 §第一性分析）的回答是否站得住？

输出格式：
- 3-5 条质疑，每条标注：
  * [F] 如果成立 → 方案应回退到方案阶段
  * [P] 如果部分成立 → 整改时需补强
  * [N] 如果不成立 → 当前方案可继续

不要输出实现层面的 bug（那是其他 4 个角色的工作）。
```

#### 输出整合

5 个角色输出后，主控汇总时增加：

```markdown
## 第一性质疑结论

### 强质疑（[F]：方案应重做）
[列]

### 中质疑（[P]：整改时需补强）
[列]

### 无效质疑（[N]：当前方案可继续）
[列]

### 决策
[若 F > 0：回退方案阶段重做]
[若仅 P：进入整改阶段，关注 P 项]
[若仅 N：进入整改阶段]
```

### 阶段 C：整改 — 验证根问题

**目标**：每改一处，标注"解决了哪个根问题"，避免修复表象留下根问题。

#### 整改记录表（台账模板演进）

**新增列**：

```markdown
| 编号 | 风险 | 严重度 | 根问题类别 | 整改方式 | 根问题是否消除 |
|------|------|--------|------------|----------|----------------|
```

**根问题类别枚举**：

| 代码 | 类别 | 描述 |
|------|------|------|
| **A** | 方案本身错 | 应回退到方案阶段，本轮整改无效 |
| **B** | 方案对，实现没到位 | 正常修复，根问题消除 |
| **C** | 方案对，实现到位但验证漏 | 加强测试 |
| **D** | 残余风险，无法根除 | 登记台账，下版本处理 |

#### 整改流程改造

**旧流程**：发现 bug → 修代码 → 跑测试 → commit

**新流程**：
1. 发现 bug
2. 标注"根问题类别"（A/B/C/D）
3. 若 A：停下，问用户是否回退方案阶段
4. 若 B/C：修代码/测试，**问自己"根问题消除了吗"**
5. 若 D：登记台账，标注下版本计划
6. commit

### 阶段 D：复核 — 验证根假设存活

**目标**：核对清单之外，验证"根假设还站得住吗"。

#### 复核报告新增"根假设存活率"

```markdown
## 复核结论

### 1. 清单核对（机械）
- ✅ 已修复：X 项
- ⚠️ 部分修复：X 项
- ❌ 未修复：X 项

### 2. 根假设存活率（第一性）
- 方案 §3 假设 A：仍然成立 ✅
- 方案 §3 假设 B：已被推翻 ⚠️（应回退方案阶段）
- 方案 §3 假设 C：仍然成立 ✅

### 3. 根问题类别回顾
- B 类（实现没到位）：X 项已修复，根问题消除
- C 类（验证漏）：X 项已补强
- D 类（残余）：X 项已登记台账
- A 类（方案错）：0 项（如有，需立即回退）

### 4. 决策建议
[若根假设有被推翻的：建议回退方案阶段]
[若根问题全部消除：可发布]
[若有 D 类未登记：补登记后再发布]
```

## 3. 第一性原理实战话术

### 3.1 提问话术（用于方案阶段）

| 问题 | 目的 |
|------|------|
| **用户在表面说什么？** | 确认需求接收 |
| **剥掉这层诉求后，用户真正想解决什么？** | 找根问题 |
| **如果用户没说"必须这样做"，最优雅的解是什么？** | 突破约束 |
| **历史有没有类似问题？怎么解决的？** | 避免重造轮子 |
| **方案最坏情况会怎样？能否回滚？** | 评估风险 |

### 3.2 质疑话术（用于评审阶段）

| 质疑 | 目的 |
|------|------|
| **"这个方案解决了真问题还是伪问题？"** | 质疑方向 |
| **"方案的根假设是什么？这些假设是否被验证？"** | 质疑根基 |
| **"如果删掉 X 功能，方案能否更简单？"** | 质疑必要性 |
| **"完成这个改动后，用户能否立即受益？"** | 质疑时机 |
| **"5 年后这个改动是否还合理？"** | 质疑长期 |

### 3.3 验证话术（用于整改 + 复核）

| 验证 | 目的 |
|------|------|
| **"根问题消除了吗？还是只是表面？"** | 避免敷衍 |
| **"如果重新发生同样场景，会再次出现吗？"** | 验证根治 |
| **"假设被推翻了吗？需要回退方案吗？"** | 复核假设 |
| **"残余风险有补偿措施吗？下版本计划有吗？"** | 闭环 |

### 3.4 Bug 模式库（来自 2026-08-20 P1-17 demo 实战）

> **本节是"事后归纳",不是"事前规则"**。每个模式都来自一次真实 demo 暴露的 bug。
> 团队遇到新 bug 时,**优先在这里追加一节**,让后人少踩一次。

#### 模式 1:Append-only Ledger 的 LIFO 语义陷阱

**症状**:ledger 是 append-only,wizard/升级/重试场景会产生多条同类型记录(如多条 `triage`),闸门逻辑遍历全部条目导致"旧记录仍生效"。

**根因**:`for e in entries: if "ready-for-human" in str(e["details"]): return wizard` 这种遍历写法,把历史状态当成"当前状态"。

**修复模板**:改为 LIFO(只看最新一条)或优先匹配最新状态:

```python
# 错误写法(把历史当状态)
for e in ledger["entries"]:
    if "ready-for-human" in str(e["details"]):
        return reject()

# 正确写法(LIFO 语义)
latest = next(
    (e for e in reversed(ledger["entries"]) if e["action"] == "triage"),
    None,
)
if latest and "ready-for-human" in str(latest["details"]):
    return reject()
```

**测试模板**:`test_intake_gate_lifo_priority_after_wizard_upgrade` —— 写 2 条同类型记录,断言"看最新"。

**预防措施**:**任何遍历 ledger 的判定逻辑,先问"要不要 LIFO"**。append-only ledger 的"全部状态"和"当前状态"是两个不同概念。

#### 模式 2:CLI 跨平台编码陷阱(emoji + GBK)

**症状**:Windows 控制台默认 GBK 编码,`typer.echo("⚠️ message")` 触发 `UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'`。

**根因**:emoji(Unicode BMP 之外,`U+1F000+`)在 GBK/CP1252 等传统编码中**不可表示**,不是"字符",是"字符编码之外的实体"。

**修复模板**:用 ASCII 标签替代 emoji:

```python
# 错误:typer.echo(f"\n⚠️  {msg}\n")
# 正确:typer.echo(f"\n[WARN] {msg}\n")
typer.echo(f"✅ OK")  # 错
typer.echo(f"[OK] done")  # 对
```

**测试模板**:断言输出**不含 BMP 之外的字符**(`ord(ch) > 0xFFFF`),而不是断言纯 ASCII —— 中文在 GBK 下可编码。

```python
for ch in output:
    if ord(ch) > 0xFFFF:
        pytest.fail(f"含 emoji/非 BMP 字符(GBK 会崩): {ch!r}")
```

**预防措施**:**所有用户可见消息,默认走 ASCII 标签**(`[WARN]` / `[OK]` / `[ERROR]`)。中文 body 可保留,但前缀必须 ASCII。

#### 模式 3:第三方库的"看似存在"API

**症状**:`type=typer.Choice([...])` 在 typer 9.x 下抛 `AttributeError: module 'typer' has no attribute 'Choice'`。

**根因**:typer 是 click 的薄封装,**不重新导出所有 click 类型**。`typer.Choice` 不存在,要用 `click.Choice`。

**修复模板**:不确定时**先 `import typer; dir(typer)` 检查实际 API**,或直接走底层 `click`:

```python
# 错误:import typer; typer.Choice(...)
# 正确:
import click
typer.prompt("...", type=click.Choice(["a", "b"]))
```

**测试模板**:真实调用一次,不要相信文档 —— demo 才能暴露。

**预防措施**:**任何"看起来应该存在的 API"都要 demo 验证一次**,单元测试用 mock 绕过时尤其危险。

#### 模式 4:中文作为测试输入的 GBK 陷阱(本次 demo 第二次踩)

**症状**:`machine.start("测试正常路径")` 在 GBK 控制台下输出乱码,`problem` 字段被截断到 < 10 字符,pydantic 抛 `String should have at least 10 characters`。

**根因**:PowerShell 默认 stdout 是 GBK,Python 字符串传到 stdout 时被编码,中文一字多字节,被 GBK 解码成乱码后**长度变短**。

**修复模板**:**测试输入统一用 ASCII**(`"test wizard trigger with enough problem text"`),中文 body 只在生产消息中使用。

**预防措施**:**测试数据是契约的一部分**,locale/编码敏感的输入必须 ASCII。

### 3.5 元模式:"先做后验" vs "先想后做"

| 模式 | 比例(本项目历史) | 适用场景 |
|------|----------------|---------|
| 单元测试能捕获的 bug | ~30% | 纯逻辑(LIFO、空值、边界值) |
| 集成 demo 能捕获的 bug | ~70% | 跨进程(编码、CLI、文件系统、locale) |

**经验法则**:**修完一个功能,先跑一次 demo 再 commit**。demo 是性价比最高的"集成测试",能在 5 分钟内暴露单元测试看不出的 70% bug。

## 4. 实战案例：DevFlow v0.3 工作区布局

### 4.1 方案阶段（按第一性 SOP 输出）

```markdown
## 第一性分析

### 1. 表象
"我希望 Spec/Plan/Review 按目录分类，便于查找和归档"

### 2. 真问题
"我希望团队的开发流程痕迹能被系统化管理，可归档、可移交、可批量处理"

### 3. 根假设
- A. 必须重组文件路径（最自然的想法）
- B. 用户能接受迁移命令（破坏性命令）
- C. 账本哈希链可以重新计算（破坏不可篡改）

### 4. 替代方案
- 替代 1：完全重组路径 + 迁移命令 + 重算哈希（v0.3 原方案）
- 替代 2：不重组文件，加 INDEX + 软归档（**第一性方案**）
- 替代 3：不做归档，等用户手动管理（不解决真问题）

### 5. 最终方案 + 对齐依据
选替代 2：
- 账本哈希链是 v0.2 P0-3 整改核心（不可破坏）
- 迁移成本高（10 文件 / 600 行）
- 替代 2 用 4 文件 / 150 行解决 80% 问题

### 6. 根风险
- 用户没有"已完成感"（软归档在视觉上无变化）
- query 性能差（每次扫所有文件）
```

### 4.2 评审阶段（4 角色 + 第一性质疑者）

```markdown
## 第一性质疑结论

### 强质疑（F：方案应重做）
[无]

### 中质疑（P：整改时需补强）
- query 性能差（每次扫所有文件）→ P1，需加索引或缓存
- "软归档在视觉上无变化" → P2，需配 CLI + 文档让用户感知

### 无效质疑（N：当前方案可继续）
- 4 角色指出的 35 个问题：大部分都是 v0.3 原方案的问题，第一性方案已规避
- 仅 P0-3（路径遍历）和 P0-5（stage 语义）仍适用，需在 query API 中处理
```

### 4.3 整改阶段（按根问题类别记录）

```markdown
| 编号 | 风险 | 严重度 | 根问题类别 | 整改方式 | 根问题是否消除 |
|------|------|--------|------------|----------|----------------|
| P0-1 | 哈希链迁移破坏 | 🔴 | A（方案错） | 改用 INDEX 方案 | ✅ 已规避 |
| P0-3 | workspace_root 路径遍历 | 🔴 | B（实现漏）| 默认路径白名单，不开放自定义 | ✅ |
| P0-5 | archive/finished/<stage>/ stage 语义 | 🔴 | N/A | 已通过方案替代消除 | ✅ |
| P1-1 | ReviewStore 路径硬编码 | 🟠 | B | 不动（旧路径仍可用） | ✅ |
```

### 4.4 复核阶段（根假设存活率）

```markdown
## 复核结论

### 1. 清单核对
- ✅ 已修复：4 项（归档、查询、自动归档、向后兼容）
- ⚠️ 部分修复：0
- ❌ 未修复：0

### 2. 根假设存活率
- 方案 §3 假设 A"必须重组文件路径"：**已被推翻** ✅（采用替代方案）
- 方案 §5 "4 文件 / 150 行 vs 10 文件 / 600 行"：**实际命中** ✅
- 方案 §6 根风险 1 "软归档视觉无变化"：**已补强** ✅（CLI archive/list-active）

### 3. 根问题类别回顾
- A 类（方案错）：1 项（P0-1）→ 已规避
- B 类（实现没到位）：2 项 → 已修复
- D 类（残余）：0 项

### 4. 决策建议
✅ 可发布。根问题全部消除或已规避。
```

### 4.5 实战案例：P1-17 Intake Wizard(2026-08-20 demo)

> **本案例是"修 bug 也走第一性 SOP"的范例**。和 §4.1 关注"设计阶段"不同,本案例关注"修复阶段"。

#### 阶段 A：方案生成 — 剥表象

**步骤 1 — 表象**:用户报告两个 P2 残留 bug:
- ⚠️17:`_gate_intake()` 没硬拒绝 `ready-for-human`,缺 wizard 模块
- ⚠️18:`_generate_handoff()` 的 `suggested_skills` 硬编码 3 个 CLI 命令

**步骤 2 — 真问题**:
- 17 是**安全门漏了**:`ready-for-human` 议题会污染 Agent 流水线
- 18 是 **UX 错位**:`suggested_skills` 是 Agent 解析的字段,不是给人类看的 CLI 列表
- 共同真问题:**架构文档承诺的"双门禁"和"动态 skill"在代码层被简化实现**

**步骤 3 — 根假设**(质疑自己会怎么修):
- A. 应该一次性把 17 和 18 都修完 → **可能错**(反小步迭代)
- B. 17 的修复 = 加个 `if` 分支 → **可能错**(闸门语义要重新定义)
- C. 18 的修复 = 改 `_generate_handoff` 输出格式 → **可能错**(数据来源问题)
- D. wizard 是新增模块 → **可能错**(wizard 可能只是个交互式 CLI 分支)
- E. 我应该严格按"双门禁"原文实现 → **可能错**(审计过 5 轮的代码可能有新边界)

**步骤 4 — 替代方案**:
- 替代 1:大方案(17+18 一起,加 wizard 模块 + 重构 handoff)
- 替代 2:**分两轮修,每轮最小化** ← 选这个
- 替代 3:只修 17,18 留给下个迭代
- 替代 4:17+18 一起但用 feature flag(增加复杂度)

**步骤 5 — 对齐约束**:
- 17 是 P1 安全门(必修),18 是 P2 UX 增强(应修)
- 分两轮 = 可独立回滚
- 选**替代 2**

**步骤 6 — 根风险**:
- 风险 1:17 修复可能引入新边界(ready-for-human 议题已走到 Stage3 怎么办?)
- 风险 2:18 修复需要决定 skill 数据来源(硬编码?配置?动态?)
- 风险 3:两次修复都可能破坏现有 121 个测试

#### 阶段 B：修复前查证(避免预判错误)

**实际查证结果**(修正了 3 个预判):
- ❌ "需要新增 `wizard.py` 模块" → **不需要**,`cli.py` 里加一个函数就够
- ❌ "需要新增 `LedgerAction.TRIAGE`" → **已经有**(`model/ledger.py:19`)
- ❌ "需要硬编码 8 个阶段的 skill 映射表" → **不需要**,`SkillResolver.resolve()` 已有 `PHASE_SKILLS` 字典

**贝叶斯更新**:**先查再改**比"先想再改"少踩 3 个坑。

#### 阶段 C：实施 + 验证

**Round 1(P1-17)**:3 个最小动作
1. 定义契约(`_gate_intake()` 的输入输出 + 拒绝语义)
2. 加最小拒绝分支(检测 ready-for-human → 返回 `{wizard: true}`)
3. 加 CLI 分支(`devflow next` 在 wizard=true 时输出交互式向导)

**Round 2(P2-18)**:3 个最小动作
1. 数据来源:从 `SkillResolver.resolve(phase)` 获取当前阶段推荐 skill
2. 结构化输出:handoff 改 `YAML frontmatter + Markdown body`
3. 动态填充:`_generate_handoff` 调 SkillResolver 而非硬编码

**全量回归**:`147 passed`(原 121 + 新增 7 + 其他历史增量)。

#### 阶段 D：Demo 验证(本案例的核心教训)

**预期**:Round 1+2 修完,bug 闭环。
**实际**:跑 demo 时暴露 **3 个修复时遗漏的 bug**:

| Bug | 根因 | 修复 |
|-----|------|-----|
| **R17-3 LIFO** | `_gate_intake` 遍历所有 triage 记录,wizard 升级后旧 ready-for-human 仍触发硬拒绝 | 改为 LIFO,只看最新一条 |
| **R17-4 GBK** | `typer.echo("⚠️ ...")` 在 Windows GBK 控制台崩溃 | 替换为 `[WARN]` |
| **R18-3 typer.Choice** | `typer.Choice` 不存在(typer 没暴露 Choice) | 改用 `click.Choice` |

**关键经验**(已写入 §3.5 元模式):
- 单元测试捕获率 ~30%,demo 捕获率 ~70%
- **修完一个功能,先跑一次 demo 再 commit** 是最高 ROI 的验证

#### 阶段 E：固化为回归测试

**新增文件**:`tests/integration/test_wizard_e2e.py`(7 个 e2e 用例)

**关键测试**:
- `test_e2e_wizard_upgrade_a_allows_next_phase`(锁定 LIFO 行为)
- `test_e2e_wizard_messages_are_ascii_safe`(锁定 GBK 兼容)
- `test_e2e_full_flow_init_start_human_wizard_recover`(全链路 demo 还原)

**全量回归**:`155 passed`(e2e 测试通过)。

#### 阶段 F：审计台账 + SOP 反哺

#### 4. 决策建议

## 7. 何时使用第一性 SOP？

| 场景 | 是否使用 |
|------|---------|
| 用户提新需求 / 新方案 | ✅ 必用（5 步拆解） |
| 重大架构变更 | ✅ 必用（4 阶段全应用） |
| 日常 bug 修复 | ❌ 跳过（用快速流程） |
| 一次性脚本 / 工具 | ❌ 跳过 |
| 紧急 hotfix | ❌ 跳过（事后复盘可补第一性分析）|

## 8. 一句话总结

> **第一性原理不是额外步骤，而是 4 个阶段的"元方法"**。
>
> 方案阶段先拆根问题、评审阶段多一个质疑者、整改阶段标注根问题类别、复核阶段验证根假设。
>
> 核心价值：**避免在错的问题上做对的事**。
