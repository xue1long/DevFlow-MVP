## 一、为什么暂停

第 6 轮审计共识(4 角色独立验证):

| 核心设计 | 被证伪的原因 |
|---|---|
| 分代哈希迁移 | v1 算法与现有全字段哈希矛盾(迁移前置检查 100% 失败) |
| migrate-ledger | 重算哈希 = 合法化篡改;中断无原子性保护 |
| LedgerEntry 加 5 字段 | spec_id 用 current_spec_id 推断 = NP0-2 同构 |
| StorageBackend 拆分 | YAGNI(0 个调用方需要 3 个子接口) |

**触发 v0.4 的真实信号**:

1. **出现第二个存储后端需求**(如 DB 后端 / 远程同步)→ 接口拆分才有意义
2. **多 spec 工作流成为主流用法**(当前用户场景 <20%)→ 才需要解决 NP0-2 根因
3. **审计合规要求 actor/session_id**(如客户/监管要求)→ 才需要账本 schema 演进

## 二、v0.4 重新设计预案(等需求触发时启用)

### 预案 A:侧车审计文件(sidecar,替代分代哈希)

```text
不再扩 LedgerEntry schema!
新增独立文件 audit/<date>.jsonl(append-only):
  {"ts": "...", "session": "...", "actor": "agent",
   "spec_id": "...", "action": "review", "round": 1}
主账本 progress.yaml 完全不动(哈希链零风险)
侧车文件用独立 hash 链或仅 append-only 约束
```

- **优点**:主账本零风险;无需迁移工具;grep 可审计
- **代价**:查询要 JOIN 两个文件(程序化代价,非用户痛点)
- **第一性判定**:✅ 更简,且不触碰哈希链

### 预案 B:多 spec JOIN 用文件名反推(替代 spec_id 字段)

```text
review_store 文件路径已是 {spec_id}/r{round}.yaml
review-audit 反查:
  1. 遍历 review_store 所有文件 → (spec_id, round) 键集合
  2. 遍历 ledger review/fix/escalate 条目,用 details 文本解析 round
  3. 结合"哪个 spec 活跃"的时间窗推断(足够审计场景)
```

- **优点**:零 schema 变更;r2 已落地单 spec 版,扩展即可
- **代价**:时间窗推断有边界误差(审计场景可接受)
- **第一性判定**:✅ 用现有数据,不扩 schema

### 预案 C:接口拆分(仅在触发信号 1 时启用)

```text
出现第二个后端时:
  FileStore / LedgerStore / StateStore 三个 ABC
  FSBackend 实现全部(向后兼容)
  新后端实现所需子集
否则:保持聚合 StorageBackend(duck typing 足够)
```

- **第一性判定**:✅ YAGNI——等真实需求
