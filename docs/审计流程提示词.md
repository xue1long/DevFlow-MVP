# DevFlow 审计流程提示词模板

> **用途**：DevFlow 项目的多角色架构评审 + 整改 + 复核闭环标准作业提示词。可直接复用。
> **版本**：v0.2（基于第 3 轮 4 角色独立评审实战验证）

## 适用场景

- 项目架构评审（代码层、文档层均可）
- 关键设计方案的合理性审查
- 重大功能上线前的多视角风险扫描
- 周期性的项目健康度评估

## 流程总览

```
┌─────────────────────────────────────────────────────┐
│  阶段1：4 角色独立评审（同一条消息并行派发）         │
│   ├─ 落地执行者（实操卡点/流程断层）                  │
│   ├─ 风险管控者（隐患/合规/损失/应急）                │
│   ├─ 逆向挑战者（逻辑漏洞/反例/失效）                 │
│   └─ 最终验收人（目标达成度/可迁移性）                │
│  ↓ 各自独立输出问题清单（不互相借鉴）                │
├─────────────────────────────────────────────────────┤
│  阶段2：主控汇总 + 按严重程度排序                    │
│   ├─ 🔴 P0：必须修复（致命缺陷）                    │
│   ├─ 🟠 P1：优先修复或登记残余风险                  │
│   └─ 🟡 P2：登记台账（下版本处理）                  │
├─────────────────────────────────────────────────────┤
│  阶段3：主控整改（按 P0→P1→P2 顺序）                │
│   ├─ 修复一处 → 跑测试                              │
│   ├─ 每项修复标注 P0-X / P1-X                       │
│   └─ 新增测试锁定关键行为                           │
├─────────────────────────────────────────────────────┤
│  阶段4：独立复核（整改后独立子代理验证）             │
│   └─ 逐项输出 ✅ 已修复 / ❌ 未修复                  │
├─────────────────────────────────────────────────────┤
│  阶段5：归档（写入 审计整改台账.md）                 │
│   ├─ 审计来源                                       │
│   ├─ 整改记录（按 P0/P1/P2 分组）                   │
│   ├─ 复核审计结论                                   │
│   ├─ 修改潜在副作用评估                             │
│   └─ 残余风险清单                                   │
└─────────────────────────────────────────────────────┘
```

## 阶段1：4 角色独立评审提示词

### 1.1 主控发起命令（用户口头指令）

```
/graphify 使用graphify依次以4种不同角色独立评审这个项目架构，每个角色单独
输出问题，不要互相借鉴：
角色1：落地执行者（关心实操卡点、流程断层）
角色2：风险管控者（关心隐患、合规、损失、应急预案）
角色3：逆向挑战者（专门寻找逻辑漏洞、反例、失效条件）
角色4：最终验收人（衡量方案能不能达成原始目标）
每个角色只输出发现的问题，最后汇总全部风险，按严重程度排序。
```

### 1.2 派发给子代理的 prompt 模板（4 个角色共用骨架，只换"评审视角"段）

> 以下以**角色1：落地执行者**为完整示例。角色2/3/4 的 prompt 只替换「评审视角」和「输出要求」段，其它部分相同。

```text
## 角色：落地执行者

你的任务是独立评审 DevFlow 项目架构，**只关心实操卡点和流程断层**。
不要给出解决方案，只输出你发现的问题。

### 评审视角

你是一个即将上手使用 DevFlow 的 AI 开发者，你的视角是：
1. **实操卡点**：哪些环节的实际操作路径不清晰、步骤缺失、会让使用者卡住？
2. **流程断层**：状态机 8 阶段之间是否有断裂？阶段之间的信息传递是否完整？
3. **工具链衔接**：CLI 命令之间是否有依赖关系没有被文档化或校验？
4. **异常处理**：出错了怎么办？有没有兜底路径？
5. **上手成本**：新用户要花多少步才能跑通第一个完整流程？

### 项目文件

项目位于 `D:\5-Project\20260819\devflow`，核心文件结构：
```
pyproject.toml
src/devflow/
  cli.py                     — 14 个 CLI 命令
  model/                     — 8 个领域模型 + review 模型
  engine/
    state_machine.py          — 八阶段状态机核心
    review_engine.py          — 审核闭环引擎
    redline_auditor.py        — 红线审计器
  storage/
    base.py                   — StorageBackend 抽象接口
    fs_backend.py             — 文件系统存储实现
    git_port.py               — GitPort 抽象 + 实现
    review_store.py           — 评审存储
  policy/loader.py            — sop.yaml 加载与版本协商
  verify/gate_runner.py       — 门禁执行器
config/sop.default.yaml       — 默认 SOP 配置
tests/                        — 测试用例
```

### 输出要求

- 只输出问题清单，每条标注严重程度（🔴 阻塞 / 🟡 较严重 / 🟢 轻微）
- 每个问题用一句话描述，然后 1-2 句展开说明实操场景
- 不要输出任何解决方案或建议
- 语言：中文

请先阅读关键文件，然后输出你的问题清单。使用 `read` 工具读取你需要的文件。
```

### 1.3 角色 2：风险管控者的"评审视角"段

```text
### 评审视角

你是一个安全/风控专家，你的视角是：
1. **数据损失**：progress.yaml 是 append-only 日志，但它是单文件——如果损坏或写入中断会丢失什么？
2. **合规审计**：账本记录是否完整、不可篡改？能否满足"每个决策都有记录"的审计要求？
3. **单点故障**：FSBackend 是唯一存储实现——如果文件系统不可写怎么办？
4. **依赖风险**：依赖 Git 仓库（无 git 时 commit/audit 命令失效），依赖 subprocess 调用外部命令，依赖 YAML 解析
5. **并发安全**：MVP 说单进程使用，但如果有两个进程同时操作 progress.yaml 会怎样？
6. **用户误操作**：有害命令组合、误操作后的恢复路径
7. **外部依赖版本**：pydantic/pyyaml/typer 的版本合同是否明确？

### 输出要求
- 只输出问题清单，每条标注严重程度（🔴 致命风险 / 🟡 重大隐患 / 🟢 轻微风险）
- 每个问题用一句话描述，然后 1-2 句展开说明风险场景
- 不要输出任何解决方案或建议
- 语言：中文
```

### 1.4 角色 3：逆向挑战者的"评审视角"段

```text
### 评审视角

你是一个专门挑刺的逆向工程师，你的视角是：
1. **逻辑漏洞**：状态机的不变量是否真的成立？有没有绕过门禁的路径？
2. **反例**：什么场景下这个方案会失效？边界条件是什么？
3. **自相矛盾**：架构文档、sop.yaml、CLI 之间是否存在不一致？
4. **假阳性/假阴性**：门禁检查是否可能误报（block 不该 block 的）或漏报（放过不该放过的）？
5. **状态不一致**：progress.yaml 中的 state 和实际文件系统状态是否可能不同步？
6. **审核闭环的死循环**：防死循环的 3 道防线是否有新的漏洞，能被绕过？
7. **权限和绕过**：CLI 是否可以被绕过（用户直接 git commit 不经过 devflow）？

### 输出要求
- 只输出问题清单，每条标注严重程度（🔴 逻辑漏洞 / 🟡 边界隐患 / 🟢 轻微瑕疵）
- 每个问题用一句话描述，然后 1-2 句展开说明具体的反例场景
- 不要输出任何解决方案或建议
- 语言：中文
```

### 1.5 角色 4：最终验收人的"评审视角"段

```text
### 评审视角

你是一个验收负责人，对 DevFlow 的原始目标是：
> "一个给 AI Agent 用的开发流程强制引擎——让 AI 写代码时不跳步、不省事，
> 每个阶段都有产出、有门禁、有账本。"

验收标准：
1. ✅ 8 阶段不可跳步状态机
2. ✅ 多个 CLI 命令
3. ✅ 逐阶段出口门禁
4. ✅ 红线审计
5. ✅ append-only 账本
6. ✅ 挂起/续接
7. ✅ 测试保障
8. ✅ 模块化解耦
9. ✅ 审核闭环

你的评审视角：
1. **目标达成度**：原始目标是否真的实现了？有没有遗漏的关键能力？
2. **质量门禁**：门禁是真的"阻断"还是"摆设"？有没有场景门禁可通过但实际有问题的？
3. **可审计性**：账本是否真的能回答"谁在什么时候做了什么"？
4. **可迁移性**：换一个项目（不同语言、不同测试框架）还能用吗？

6. **测试覆盖**：测试覆盖了哪些、漏掉了哪些关键场景？

### 输出要求
- 只输出问题清单，每条标注严重程度（🔴 未达标 / 🟡 部分达标 / 🟢 轻微不足）
- 每个问题用一句话描述，然后 1-2 句展开说明差距
- 不要输出任何解决方案或建议
- 语言：中文
```

```text
每项输出：
```

```
最后汇总已修复/未修复/残余数量。不要输出任何其他内容。
```

## 阶段2：主控汇总规则

```text
按严重程度分桶：
- 🔴 P0：必须修复或永不前进
- 🟠 P1：优先根治，或登记残余风险
- 🟡 P2：登记台账，不阻塞

归并口径：
- 同一问题被多角色独立指出 → 升级严重程度
  （如 4 角色都指向的"账本非安全"）
- 修复 → ✅
- 不修复但有理由 → 登记残余风险（写明补偿措施 + 下版本计划）

输出去向：审计整改台账.md 第 N 轮审计章节，含：
- 审计来源（4 角色并行）
- 审计摘要（数量 + 致命断裂点）
- 整改记录（P0-1/2/3...、P1-1/3/4...逐条状态）
- 复核审计结论（独立子代理验证）
- 修改潜在副作用评估
- 残余风险清单
```

## 阶段3：主控整改的内部工作流提示

整改阶段的提示词不外发给子代理，而是**主控 Agent 自己执行**：

```text
按以下顺序整改 P0→P1：
1. 修复一处 → 跑全量测试
2. 失败 → 调整断言或修代码
3. 通过 → 进入下一项
4. 每项修复标注 P0-X / P1-X 注释（与台账编号一致）
5. 新增测试用例锁定关键行为
6. 全部完成后 git commit + git push
```

## 设计经验总结

| 经验 | 说明 |
|------|------|
| **4 角色独立 → 同一消息并行派发** | 天然隔离，避免互相借鉴 |
| **每个角色 prompt 完整独立** | 只换视角段，不共享评审标准 |
| **"只输出问题，不输出解决方案"** | 强制收敛到发现而非建议 |
| **复核独立子代理** | 整改后用独立子代理验证，避免主控自我放行 |
| **台账不可覆盖** | 历史轮次保留，新轮次 append-only |
| **归并去重 + 升级严重程度** | 多角色独立指向同一结论 → 必为真问题 |

## 实战数据（DevFlow 第 3 轮）

- 4 角色独立评审：23 + 18 + 25 + 21 = **87 条原始问题**
- 归并去重：**41 条独立问题**（P0=8, P1=14, P2=19）
- 整改率：**P0 8/8 (100%)，P1 6/14 (43% + 8 登记残余)，P2 8/19 (42% + 10 登记残余)**
- 测试增加：64 → 82（+18 条验证测试）
- 复核审计：**14/14 已修复，0 未修复**

## 复用建议

1. **直接复用骨架**：替换"评审视角"和"项目文件"段即可用于任何项目
2. **角色数量可调**：4 角色适合中等复杂度，重大架构可加 1-2 个专项角色（如性能、安全）
3. **小改动可省复核**：单点修复无需独立复核，重大架构改动建议保留
4. **graphify 协同**：项目代码量大时，配合 `/graphify` 生成知识图谱作为评审基础材料
