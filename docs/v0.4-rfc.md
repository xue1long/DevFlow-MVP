## 二、核心设计决策:哈希链兼容方案

> 这是 v0.4 最大的技术难点,也是 v0.3.1-r1 被回退的根本原因。
> **必须正面解决,不能绕过。**

### 2.1 问题陈述

`fs_backend.py:107-120` `_compute_entry_hash` 用 `json.dumps(content, sort_keys=True)` 序列化**整个 entry dict**(仅排除 `_hash/_prev_hash`)。

```
后果: LedgerEntry 加任何字段 → 新条目的哈希字节变化 → 与旧条目的 prev_hash 链接不连续
       → verify_ledger 从第一个新字段写入处开始全部报失败
```

### 2.2 候选方案对比(第一性原则)

| 方案 | 思路 | 优点 | 缺点 | 第一性判定 |
|---|---|---|---|---|
| **A: 字段白名单哈希** | `_compute_entry_hash` 改为只哈希固定核心字段集(phase/action/timestamp/details/spec_id/actor/...) | 简单 | 新字段不进哈希 → 可被篡改而不被发现,削弱"不可篡改"承诺 | ❌ 削弱审计价值 |
| **B: 分代哈希(推荐)** | 账本顶层加 `ledger_version`;v0.4 写入用新哈希算法(含全部字段);旧账本迁移时用 `migrate-ledger` 一次性重算整条链 | 完整保留不可篡改承诺 | 需要迁移工具 + 迁移后不可回退 | ✅ **采用** |
| **C: 双账本** | 新字段写入独立 sidecar 文件,主账本不动 | 主账本零变化 | 审计完整性割裂,查询要 JOIN 两个文件 | ❌ 过度复杂 |

### 2.3 方案 B 详细设计(分代哈希 + 迁移)

**账本顶层新增字段**:

```yaml
ledger_version: "2.0"        # 新增:账本 schema 版本
schema_migrated_at: null     # 新增:迁移时间戳
current_spec_id: ...         # 已有
current_plan_id: ...         # 已有
current_phase: ...           # 已有
chain_head: ...              # 已有
entries: [...]               # 已有
```

**`_compute_entry_hash` 分代实现**:

```python
# fs_backend.py
_HASH_FIELD_ORDER_V1 = ("phase", "action", "timestamp", "details")  # v0.3 及之前
_HASH_FIELD_ORDER_V2 = (
    "phase", "action", "timestamp", "details",
    "spec_id", "actor", "session_id", "review_ref",  # v0.4 新增字段
)

def _compute_entry_hash(self, entry: dict, prev_hash: Optional[str],
                        ledger_version: str = "2.0") -> str:
    """分代哈希:按 ledger_version 选择字段集

    v1 账本: 只哈希核心字段(旧链兼容,新字段会被忽略 → 迁移前的新条目不进账本)
    v2 账本: 哈希全部字段(含 v0.4 新字段,完整不可篡改)
    """
    if ledger_version == "1.0":
        fields = _HASH_FIELD_ORDER_V1
    else:
        fields = _HASH_FIELD_ORDER_V2
    content = {k: entry[k] for k in fields if k in entry}
    entry_json = json.dumps(content, sort_keys=True, ensure_ascii=False)
    h = hashlib.sha256()
    h.update(entry_json.encode("utf-8"))
    if prev_hash:
        h.update(prev_hash.encode("utf-8"))
    return h.hexdigest()
```

**`migrate-ledger` 迁移命令**(新 CLI):

```python
@app.command(name="migrate-ledger")
def migrate_ledger():
    """v0.4: 把 v1 账本迁移到 v2 schema(一次性,不可回退)

    步骤:
    1. 读旧账本(v1)
    2. 对每条 entry:补 spec_id(从 ledger 顶层 current_spec_id 推断,或留空)
       + actor(null) + session_id(null) + review_ref(null)
    3. 用 v2 哈希算法重算整条链(从第一条开始)
    4. 写新账本(ledger_version: 2.0)
    5. 写迁移日志(迁移前 hash 存档,供审计)
    """
```

**迁移前置检查**:

```python
def _pre_migrate_check(ledger: dict) -> dict:
    """迁移前检查:
    1. 旧账本 verify_ledger 是否通过(不通过不迁移)
    2. 是否已迁移(ledger_version == "2.0" → 拒绝重复迁移)
    3. 备份旧账本到 progress.yaml.bak-v1
    """
```

### 2.4 兼容性影响

- ✅ **旧账本(v1)可读**:`verify_ledger` 自动检测 `ledger_version`,v1 用旧算法验证
- ✅ **新账本(v2)完整**:全部字段进哈希,不可篡改承诺完整保留
- ⚠️ **迁移后不可回退**:v2 账本无法用 v1 代码读取(旧代码不认 `ledger_version: "2.0"`)
- 🔧 **迁移工具**:`devflow migrate-ledger` 一键迁移,迁移前自动备份

### 3.1 P1-10:账本 actor / session_id(P1 重大,2d)

**背景**:账本条目无"谁在何时做了什么"信息,审计无法追溯操作者。

**设计**:LedgerEntry 新增 2 个字段(v2 哈希包含):

```python
class LedgerEntry(BaseModel):
    # ...已有字段...
    spec_id: Optional[str] = Field(default=None, description="v0.4: 关联的 Spec ID(多 spec 追溯)")
    actor: Optional[str] = Field(default=None, description="v0.4: 操作者标识(agent/human/CI)")
    session_id: Optional[str] = Field(default=None, description="v0.4: 会话 ID(一次 CLI 调用)")
```

**写入时机**:`append_ledger` 内部自动填充 session_id(每次 CLI 进程启动生成 UUID);actor 由调用方传入(默认 "agent")。

**CLI 装配**(cli.py):

```python
def _get_session_id() -> str:
```

### 3.2 P1-13 完整:多 spec 双向 JOIN(P1 重大,2d)

**背景**:r2 的 `review-audit` 用 `current_spec_id` 关联,多 spec 工作流系统性误报。根因:LedgerEntry 缺 `spec_id` 字段。

**设计**(依赖 3.1 的 spec_id 字段):

1. `LedgerEntry.spec_id` 在写入时由 `storage.get_current_spec_id()` 自动填充
2. `review-audit` 完整版:

```python
@app.command(name="review-audit")
def review_audit():
    """v0.4 完整版:多 spec 双向 JOIN

    正向(ledger → store):
      for entry in entries where action in (review, fix, escalate):
        (entry.spec_id, round_from_details) not in report_keys → orphan
    反向(store → ledger):
      for (spec_id, report) in report_keys:
        该 (spec_id, R{report.round}) 是否在 ledger 的 review 条目中出现?
        not found → missing_in_ledger(报告写了但账本没记)
    """
```

**反向校验 `missing_in_ledger`**(P1-r2-2):

```python
    missing_in_ledger = []
    for spec_id, report in all_reports:
        found = any(
            e.get("spec_id") == spec_id
            and f"R{report.round}" in e.get("details", "")
            for e in review_actions
        )
        if not found:
            missing_in_ledger.append({
                "spec_id": spec_id,
                "round": report.round,
                "message": "review_store 有报告但 ledger 无记录(审计盲点)",
            })
```

**测试**:
- 多 spec 下各 spec 的 review 条目正确关联
- 反向检测:手工删 ledger 条目 → missing_in_ledger 报出

```python
def _check_no_test(self) -> list[RedLineViolation]:
```

### 3.4 P1-5 完整:status 字段 + 配置驱动 audit(P1 重大,1.5d)

**背景**:r2 让 stub 返回 `skip=True` 但无结构化 status;审计输出仍难区分 mvp_skip / stub / not_implemented。

**设计**:`RedLineViolation` 加 `status` 字段(4 态):

```python
class RedLineViolation:
    """红线违规"""
    def __init__(self, rule: str, message: str, skip: bool = False,
                 status: str = "active"):
        self.rule = rule
        self.message = message
        self.skip = skip
        self.status = status  # v0.4: active | mvp_skip | stub | not_implemented

    def to_dict(self) -> dict:
        return {
            "rule": self.rule,
            "message": self.message,
            "skip": self.skip,
            "status": self.status,  # v0.4 新增
        }
```

**audit() 完整版**:

```python
def audit(self) -> list[RedLineViolation]:
    """配置驱动循环:
    - mvp_skip: true → status="mvp_skip", skip=True
    - checker 不存在 → status="not_implemented", skip=True
    - checker 返回 [] (stub) → status="stub", skip=True
    - checker 返回违规 → status="active", skip=False
    """
```

**关键区别(r2 vs v0.4)**:r2 靠 `message` 文本判断,`to_dict()` 丢失 status;v0.4 加结构化字段,CLI/API/CI 都能消费。

**测试**:
- 4 态 status 正确赋值
- to_dict 含 status
- audit 输出的 coverage 统计用 status 而非 message 文本

### 3.5 P2-18:StorageBackend 接口拆分(P2 优化,2d)

**背景**:`storage/base.py` 混了 4 类职责:文件存储(Spec/Plan)+ 账本 + 阶段状态 + handoff。

**设计**:拆为 3 个接口:

```python
# storage/base.py → 拆为

class FileStore(ABC):          # 文件读写(Spec/Plan/Report)
    @abstractmethod
    def write_spec(self, spec_id: str, data: dict) -> Path: ...
    @abstractmethod
    def read_spec(self, spec_id: str) -> Optional[dict]: ...
    @abstractmethod
    def write_plan(self, plan_id: str, data: dict) -> Path: ...
    @abstractmethod
    def read_plan(self, plan_id: str) -> Optional[dict]: ...

class LedgerStore(ABC):        # 账本 + 哈希链
    @abstractmethod
    def append_ledger(self, entry: LedgerEntry) -> None: ...
    @abstractmethod
    def get_ledger(self) -> dict: ...
    @abstractmethod
    def verify_ledger(self) -> dict: ...
    @abstractmethod
    def migrate_ledger(self) -> dict: ...   # v0.4 新增

class StateStore(ABC):         # 工作区状态
    @abstractmethod
    def get_current_phase(self) -> int: ...
    @abstractmethod
    def set_current_phase(self, phase: int) -> None: ...
    @abstractmethod
    def get_current_spec_id(self) -> Optional[str]: ...
    @abstractmethod
    def set_current_spec_id(self, spec_id: Optional[str]) -> None: ...
    # ... handoff ...
```

**FSBackend 实现 3 接口**,内部共享文件系统;engine 层按需注入:

```python
# cli.py 装配
storage = FSBackend(_get_root())
file_store, ledger_store, state_store = storage, storage, storage  # 单实现多接口
```

**兼容**:StorageBackend 保留为聚合接口(3 个子接口的组合),旧调用方不受影响;新代码按子接口注入。

**测试**:
- 3 个接口各自的方法在 FSBackend 上可用
- 旧 StorageBackend 聚合接口仍可用(向后兼容)

### 3.6 P2-14:门禁结果持久化(P2 优化,0.5d)

**背景**:门禁结果不写账本,无法追溯 stdout/stderr。

**设计**:账本 entry 增加可选 `gate_result` 字段(v2 哈希包含):

```python
@app.command(name="gate")
def gate(phase: int = ...):
    result = machine.run_gate(phase)
    if result.get("stdout") or result.get("stderr"):
        storage.append_ledger(LedgerEntry(
            phase=phase,
            action=LedgerAction.GATE,
            details=f"门禁 {phase_name} 结果: {result.get('message', '')}",
            gate_result={
                "ok": result.get("ok"),
                "stdout_tail": (result.get("stdout") or "")[-500:],
                "stderr_tail": (result.get("stderr") or "")[-500:],
            },
        ))
```

**测试**:
- gate 结果写入账本,含 stdout/stderr 尾部
- verify_ledger 对新字段完整校验

## 四、迁移策略

### 4.1 迁移流程

```
v0.3.1-r2 → v0.4.0

Step 1: 升级代码(v0.4.0 发布)
Step 2: 用户运行 devflow migrate-ledger(自动检测 ledger_version)
        ├─ v1 账本 → 备份 progress.yaml.bak-v1 → 重算 v2 哈希链
        └─ v2 账本 → 提示"已迁移,无需操作"
Step 3: 用户继续使用(不可回退 v1)
```

### 4.2 迁移测试

```
- 空账本迁移: v1 空 → v2 空,ledger_version=2.0
- 单条目迁移: v1 1 条 → v2 1 条,哈希重算,verify 通过
- 多 spec 迁移: v1 多条目 → v2 多条目,spec_id 从 current_spec_id 推断
- 已迁移检测: 重复运行 migrate-ledger → 拒绝
- 迁移前 verify 失败: 拒绝迁移,提示先修复
```

### 4.3 回滚策略

- **代码回滚**:pip install devflow==0.3.1-r2 即可回滚代码
- **数据回滚**:迁移前自动备份 progress.yaml.bak-v1,可手动恢复
- ⚠️ 恢复后需删除 v2 账本(否则 v1 代码读 v2 会失败)
